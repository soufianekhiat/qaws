# Contributing to Qaws

Thank you for your interest in contributing to Qaws.

## Building

Qaws uses **Sharpmake** (primary) or **CMake** (backup).

```bash
# CMake
cmake -B build -DQAWS_SCALAR_IS_FLOAT=ON
cmake --build build --config Release
ctest --build-config Release --output-on-failure

# Sharpmake
sharpmake /sources(@'buildsystem/sharpmake/src/main.sharpmake.cs')
```

### Build options

| Option | Default | Effect |
|---|:---:|---|
| `QAWS_SCALAR_IS_FLOAT` | `ON` | which precision callers' unsuffixed names mean; the library holds both (`_f32`, `_f64`) |
| `QAWS_ENABLE_SIMD` | `OFF` | AVX2 / SSE2 / NEON batch eval |
| `QAWS_ENABLE_WARNINGS` | `ON` | Compiler warnings |
| `QAWS_WARNINGS_AS_ERRORS` | `ON`(f64) / `OFF`(f32) | `-Werror` / `/WX` |

## Parameter convention

Qaws follows the parameter convention of
[Alwan](https://github.com/soufianekhiat/alwan/blob/v3/CONTRIBUTING.md),
shared with Suwar and Abaad (docs/parameter_convention_plan.md):

| # | Rule |
|---|---|
| R1 | The context (and the allocator, the executor) is the last parameter. |
| R2 | A `*_stride` follows the buffer it strides. |
| R3 | Outputs come before inputs. |
| R4 | Sizes (`count`, `*_count`, `capacity`, `dim`) come after the buffers. |

The full order, for objects as Abaad does it:
1. plain outputs (`out_*`, a new object `T**`, `QAWS_OUT` in the shader
   cores);
2. reports and statistics;
3. in-out buffers (positions updated in place, accumulated gradients and
   adjoints);
4. the object handle (an opaque struct: no public header gives it a body);
5. input buffers (const pointers to scalars or to data structs), each
   followed by its stride;
6. sizes;
7. descriptors and options (`*_desc`, zero meaning the default);
8. enums, flags, scalars, callbacks and their user data;
9. the context, allocator and executor.

Constructors put the new object first:
`qaws_curve_create_bezier(&curve, &desc)`. Destructors take one argument.

`tools/qaws_api_tool.c` checks every declaration of the public, internal
and core headers (CTest `qaws_api_convention`). `qaws_api_tool survey
-order` prints, for a declaration out of order, its order as old indices.

## Both precisions

Every scalar-bearing function and type exists as `name_f32` and
`name_f64` in the one library. Each source is compiled through two wrappers
generated by the build systems, never directly. `qaws_names.h` maps every
precision-bearing name to `QAWS_SFX(name)`; regenerate it after adding or
renaming a declaration:

```bash
qaws_api_tool names -once qaws_status.h qaws_batch_executor.h -- <the other public headers> internal/*.h exact/*.h core/*.h simd/*.h > qaws_names.h
```

CTest `qaws_api_names` fails while it is stale. A new public header follows
the existing ones: `qaws_platform.h` first, a guard per precision
(`QAWS_<NAME>_H_F32` / `_F64`), enums in once-only guards.

## Code style

- C11 standard, no compiler extensions (`C_EXTENSIONS NO`)
- Public API prefixed with `qaws_`
- All fallible functions return `qaws_status`
- Tab indentation in source files
- No external dependencies — C11 standard library only (`<math.h>`, `<stdlib.h>`, `<string.h>`)

## Testing

Tests live in `tests/` and follow the `XX_name.c` naming convention. Each file exports a single `test_XX_name_main(void)` function that returns 0 on success or 1 on failure. The `test_runner.c` file calls all test mains sequentially.

To add a new test:

1. Create `tests/XX_name.c` (pick the next available index)
2. Include `test_common.h`
3. Write test functions using `TEST_ASSERT` / `TEST_ASSERT_STATUS`
4. Export a `test_XX_name_main(void)` function that calls them
5. Add a forward declaration and registry entry in `test_runner.c`
6. Add the file to `tests/CMakeLists.txt`

Run the suite:

```bash
cmake --build build --target check
```

## Adding a curve family

1. Create `src/qaws/qaws_<family>.h` with the descriptor struct and `qaws_curve_create_<family>`
2. Create `src/qaws/qaws_<family>.c` implementing creation and the eval vtable
3. Add `QAWS_CURVE_KIND_<FAMILY>` to `qaws_types.h`
4. Include the header in `qaws.h`
5. Add the `.c` file to `QAWS_SOURCES` in `CMakeLists.txt`
6. Add the `.h` to the install list in `CMakeLists.txt`
7. Write tests and documentation

## Pull requests

- One logical change per PR
- Tests must pass for both f32 and f64 configurations
- New public API functions need documentation in `docs/api/`
